# Drover widgets

WidgetKit extensions for iOS, macOS and watchOS. They show the fleet summary (`native.summary`) from the Drover daemon.

## What they show

| platform | widget | families |
|---|---|---|
| iOS | Fleet summary | small, medium, large |
| iOS | Waiting on you | accessory circular, rectangular, inline (lock screen) |
| macOS | Fleet summary | small, medium, large |
| watchOS | Waiting on you | accessory circular, rectangular, inline, corner |

Fleet summary shows sessions waiting on you, working and idle. Waiting on you shows how many sessions need you and the top one.

## Data flow

- The App Group `group.dev.drover` holds `summary.json`, the bare `result` object of `native.summary`. The apps write it, and the widget writes it too when it fetches on its own. The file modification date is the fetch time.
- The widget reads only the read-only widget token: Keychain service `dev.drover.token`, account `widget` (never `main`), through the shared access group `$(AppIdentifierPrefix)dev.drover.shared`.
- The base URL comes from `UserDefaults(suiteName: "group.dev.drover")`, key `drover.baseURL`. The apps write it.
- Refresh policy: the timeline asks WidgetKit for a reload after 5, 10 or 15 minutes depending on state. The system decides when it really runs.
- Deep links: tapping a session opens `drover://session/<id>?host=<host>` (the id is percent-encoded as one path segment, host omitted when empty). Other taps open `drover://board`.

## Host filter

Each widget takes a Host setting (`HostFilterIntent`): empty shows all hosts, or pick one. The choices are the hosts in the cached summary. A saved choice survives a cache miss. watchOS has no configuration UI, so the watch offers recommendations: All hosts plus up to 4 cached hosts.

## Checking without Xcode

```
Widgets/script/check.sh
```

This runs `swift test` for the Foundation-only core (summary decoding, cache, fetch parsing, refresh policy, deep
links, and core's shared `Fixtures/` once they are on main) and a `swiftc -typecheck` of every widget source against the real iOS, macOS and watchOS SDKs. It proves the code compiles and the core logic works. It does not prove the extension links, signs, passes entitlements, renders correctly or runs on a device.

## Project wiring

`Bundles/*/Info.plist` and `*.entitlements` are generated by XcodeGen from `properties:` in `project.part.yml`; edit them
there.

`project.part.yml` defines `DroverWidgets-iOS`, `DroverWidgets-macOS` and `DroverWidgets-watchOS`. A root `project.yml` includes it, and each app embeds its extension under `dependencies` (`- target: DroverWidgets-iOS` and so on).

## What the host apps must do

- Embed the matching extension target.
- Register the `drover` URL scheme and handle `drover://session/...` and `drover://board`.
- Write the cache (`summary.json`), `drover.baseURL`, and the Keychain `widget` item.
- Enable the App Group `group.dev.drover` and the Keychain group `$(AppIdentifierPrefix)dev.drover.shared` in their own entitlements.
- Call `WidgetCenter.shared.reloadAllTimelines()` after writing the cache, and
  `invalidateConfigurationRecommendations()` when its host list changed (the watch builds its choices from it).
- The watch app fills the watch's own App Group container.

## What the owner must do

- Set `DROVER_TEAM_ID` for the root project.yml (the widget targets inherit `DEVELOPMENT_TEAM` from it).
- Register the App Group and the Keychain group in the developer portal for all bundle ids.
- Accept the Xcode license so `xcodebuild` works.

## Known limits

- WidgetKit has a refresh budget; updates can be late and there is no push.
- On macOS the `group.dev.drover` form needs a provisioning profile that grants it. Without one, a sandboxed
  macOS 14 app must use the team-prefixed form (`<TEAMID>.dev.drover`) in the apps and the macOS widget alike.
- Plain http to a daemon on loopback, LAN, raw IP or `*.ts.net` relies on the ATS keys in the generated Info.plist;
  not yet confirmed on a device.
- Never run on a device yet; only type-checked and unit-tested.
